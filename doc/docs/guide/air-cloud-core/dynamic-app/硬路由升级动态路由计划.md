# AirForge 硬路由升级动态路由计划

## 1. 背景

当前请求链路由 `air.gateway` 进入 `air.forge`。AirForge Gateway 目前把 `/mods/{modId}/...` 当作固定寻址协议：从路径第一段解析 Mod，再使用全局 `DynamicAppId` 查询运行目标。实例上的 `RoutePrefix` 同时承担服务路由和网关入口路由，导致应用、Mod、版本、实例与入口路径强绑定。

这种设计在路由变化、应用标识迁移或同一服务存在多个入口时容易失效。入口路径一旦不再符合 `/mods/{modId}`，即使目标实例健康运行，AirForge 也可能在转发前返回 `dynamicapp.gateway.target_not_found`。

本计划将 AirForge 从“按应用和 Mod 固定解析的硬路由”升级为“独立路由映射表驱动的动态路由”。

## 2. 目标

### 2.1 请求职责边界

```text
客户端
  -> air.gateway
  -> air.forge
  -> AirForge 路由映射匹配
  -> 目标 DynamicApp / Mod / Deployment
  -> 下游路径模板重写
  -> 业务实例
```

- `air.gateway` 只负责入口接收和转发到 `air.forge`，不负责选择业务实例。
- `air.forge` 只根据自身路由映射决定目标应用、目标 Mod、目标实例和下游路径。
- AirForge 不解释上游路径的业务含义，也不从上游路径推断应用或 Mod。
- `/mods/system` 可以作为任意路由的下游路径，不再是 AirForge 固定的寻址协议。
- 目标实例未指定时，从目标 Mod 的可用实例中按该路由独立轮询；转发前仍按生命周期和健康状态判断是否可接收流量。
- 目标实例已指定时，只转发到指定 Deployment；指定实例不存在或当前不可用时返回明确错误，不静默切换实例。
- `TargetVersion` 是可选约束，允许保存指向当前不可用的版本；保存时必须展示不可用原因并要求二次确认，实际转发前必须重新校验目标状态。

### 2.2 典型映射

入口请求由 `air.gateway` 转到 AirForge 后，AirForge 可以配置：

```text
上游路径：/001/002/{path}
目标应用：fcj-platform
目标 Mod：system
目标实例：未指定，轮询
下游路径：/mods/system/{path}
```

请求：

```text
/001/002/fcj_common_api/manage/init
```

转发到目标实例：

```text
http://127.0.0.1:5111/mods/system/fcj_common_api/manage/init
```

另一个映射也可以将：

```text
/hffcj_common_api/{path}
```

转发为：

```text
/fcj_common_api/{path}
```

上游前缀和下游前缀之间不建立硬编码关系，全部由路由映射配置决定。

## 3. 非目标

- 不改变 `air.gateway` 的 Ocelot 业务路由职责之外的现有能力。
- 不修改业务 Mod 的 Controller、动态 API 或真实业务接口。
- 不把入口路由写回 Manifest 的业务配置。
- 不因为增加动态路由而自动重启、停止或重建业务实例。
- 不删除现有实例状态、包文件、部署目录和日志数据。

## 4. 现状问题与边界调整

### 4.1 当前硬路由

当前 Gateway 逻辑近似为：

```text
请求路径必须匹配 /mods/{modId}/...
从第一段解析 modId
使用 Gateway 全局 DynamicAppId + modId 查找实例
根据实例 RoutePrefix 剥离路径
```

升级时直接移除以下假设，不保留硬路由 fallback 或旧路由兼容入口：

- 上游路径必须以 `/mods` 开头。
- 上游路径的第一段一定是 ModId。
- Gateway 全局 `DynamicAppId` 能代表所有入口路由的目标应用。
- `DynamicAppRouteTarget.RoutePrefix` 同时表示入口路径和下游业务路径。

### 4.2 新职责

```text
运行状态：描述谁在运行、实例是否健康、实例地址是什么
路由映射：描述什么上游路径转给谁、选择哪个实例、改写成什么下游路径
```

两者通过 `DynamicAppId + ModId + Version + DeploymentId` 关联，但不再共享入口路径字段。

## 5. 路由映射模型

新增独立的 `DynamicAppGatewayRoute` 模型，建议字段如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `RouteId` | string | 稳定的路由规则标识，创建后不可隐式改变 |
| `Name` | string | 管理页面显示名称 |
| `UpstreamPathTemplate` | string | AirForge 接收到的上游路径模板 |
| `UpstreamHttpMethods` | string[] | 允许的 HTTP 方法；为空表示所有方法 |
| `TargetDynamicAppId` | string | 目标 DynamicApp 标识 |
| `TargetModId` | string | 目标 Mod 标识 |
| `TargetVersion` | string? | 可选版本；与 `TargetDeploymentId` 互斥，空值表示按当前健康实例轮询 |
| `TargetDeploymentId` | string? | 可选实例；与 `TargetVersion` 互斥，指定实例时实例自身确定所属版本 |
| `DownstreamPathTemplate` | string | 发给业务实例的下游路径模板 |
| `Order` | int | 手动指定匹配顺序，数值越小越先匹配 |
| `Enabled` | bool | 是否参与匹配 |
| `CreatedAtUtc` | DateTimeOffset | 创建时间 |
| `UpdatedAtUtc` | DateTimeOffset | 更新时间 |
| `LastStatusMessage` | string | 最近一次校验或转发状态 |

示例：

```json
{
  "routeId": "system-common-api",
  "name": "System Common API",
  "upstreamPathTemplate": "/001/002/{path}",
  "upstreamHttpMethods": [ "GET", "POST", "PUT", "DELETE" ],
  "targetDynamicAppId": "fcj-platform",
  "targetModId": "system",
  "targetVersion": null,
  "targetDeploymentId": null,
  "downstreamPathTemplate": "/mods/system/{path}",
  "order": 100,
  "enabled": true
}
```

### 5.1 模板约束

- 必须是绝对路径，以 `/` 开头。
- 不允许携带查询字符串、片段、反斜杠或完整 URL。
- 首期按 Ocelot 风格支持固定段、单段命名参数和尾部 `{path}`/`{everything}` 捕获参数；后续再扩展其他参数语法。
- 上游和下游模板的参数名称必须能够对应，避免参数丢失。
- 模板匹配必须按路径段边界进行，`/api` 不能误匹配 `/apiv2`。
- 查询字符串默认原样转发，不参与路径模板匹配。

## 6. 匹配与转发流程

### 6.1 匹配顺序

1. 忽略 `Enabled = false` 的规则。
2. 按 HTTP 方法过滤。
3. 按 `UpstreamPathTemplate` 匹配并提取路径参数。
4. 按 `Order` 升序排序，严格按照排序后的规则逐条转发。
5. 路由完全相同（上游模板和允许方法相同）时配置冲突。
6. 不完全相同但存在父子关系时，子路由的 `Order` 必须小于父路由；否则父路由会先命中并阻断子路由。
7. 没有匹配规则时返回结构化 404，并记录 `route_not_found`。

### 6.2 目标解析

1. 使用规则中的 `TargetDynamicAppId`、`TargetModId` 查询运行状态。
2. `TargetVersion` 为空时选择当前可用版本；填写时只允许该版本，不要求保存时已经 `Active + Healthy`。
3. `TargetDeploymentId` 有值时只检查该实例。
4. `TargetDeploymentId` 为空时筛选所有 `Active + Healthy` 实例。
5. `TargetVersion` 与 `TargetDeploymentId` 同时有值时拒绝配置；路由只保存目标值，不绑定实例生命周期。
6. 指定实例不存在、停止或不健康时，不降级到其他实例，返回明确的目标不可用错误。
7. 未指定实例且没有健康实例时返回目标不可用错误。

### 6.3 轮询

- 每条路由使用独立轮询计数器，键为 `RouteId`。
- 轮询候选按稳定顺序排序后再计算索引，避免状态文件顺序变化造成不可预测跳转。
- 候选实例发生变化时自动重新计算，不固定绑定旧 PID。
- 转发时只对当前允许接收流量的实例生效，`Draining`、`Failed`、`Unhealthy` 不接收新请求；指定不可用目标不得降级。

### 6.4 下游 URI

```text
下游 BaseAddress = 目标实例地址
下游 Path = DownstreamPathTemplate 替换后的路径
下游 Query = 原请求 QueryString
```

目标实例的 `BaseAddress` 只表示主机和端口，下游路径完全由动态路由模板决定。`RoutePrefix` 属于旧路由模型，升级过程中删除，不保留兼容元数据。

## 7. 持久化与并发

新增独立路由文件，例如：

```text
data/dynamicapp-gateway-routes.json
```

新增 `IDynamicAppGatewayRouteStore`，至少提供：

- `ListAsync`
- `GetAsync`
- `CreateAsync`
- `UpdateAsync`
- `RemoveAsync`
- `SetEnabledAsync`

要求：

- 使用原子临时文件写入，避免进程重启时产生半个 JSON 文件。
- `RouteId` 唯一，不允许静默覆盖其他规则。
- 更新使用版本号或 `UpdatedAtUtc` 乐观并发校验。
- 写入前校验模板、方法、目标字段和优先级。
- 路由变更只更新路由文件，不修改实例进程和包目录。
- Host 重启后自动加载路由表；路由表损坏时保留旧快照并报告明确错误。

## 8. Manager API

新增独立路由映射 API，建议挂在现有 Manager API 前缀下：

```text
GET    /routes
GET    /routes/{routeId}
POST   /routes
PUT    /routes/{routeId}
DELETE /routes/{routeId}
POST   /routes/{routeId}/enable
POST   /routes/{routeId}/disable
PUT    /routes/{routeId}/enabled
POST   /routes/validate
```

接口行为：

- 创建和更新时校验路由完全重复、父子顺序、目标字段和下游模板合法性。
- 当 `TargetVersion` 或指定 Deployment 当前不可用时，返回原因、影响范围和二次确认标记；只有确认后才允许保存。
- 删除路由只删除映射，不停止目标实例。
- 禁用路由只停止新请求匹配，不影响已有连接。
- 查询返回目标实例摘要、当前可用实例数、匹配状态和最近错误。
- 删除旧 `/routes/update` 接口，不保留兼容层；路由管理只使用独立动态路由 CRUD、校验和启停接口。

## 9. AirForge 页面

路由管理全面改为独立“入口路由映射”视图，不再编辑或展示入口 `RoutePrefix`，字段为：

- 路由名称与 RouteId
- 上游路径模板
- HTTP 方法
- 目标应用
- 目标 Mod
- 目标版本
- 实例选择：自动轮询 / 指定实例
- 下游路径模板
- Order 排序序号
- 启用状态
- 当前匹配结果与健康实例数

编辑体验：

- 目标应用、目标服务、目标版本、目标实例全部使用级联选择器，不让用户手写内部键。
- 路由目标方式分为“按版本”和“按实例”；按版本时选择版本或保留自动选择，按实例时只选择实例，版本字段失效。
- 选择应用和服务后，版本和实例下拉只显示该目标的候选值；版本和实例互斥。
- 路由只保存目标字符串，不参与服务启停、删除和销毁关联。
- 保存前显示最终转发示例：上游请求、选中的目标实例、下游请求。
- 路由冲突、模板参数不一致、目标不可用时在表单内直接提示；目标不可用时必须二次确认后才保存。
- 路由完全相同、父子顺序错误时禁止保存。

## 10. 迁移策略

### 阶段一：动态路由内核

- 增加独立动态路由 Store、Ocelot 风格通用模板解析器、匹配器、顺序校验器和目标选择器。
- Gateway 只接受动态路由规则，不再从入口路径解析 ModId，不再使用全局 `DynamicAppId` 筛选入口路由。
- 删除 `DynamicAppRouteTarget.RoutePrefix` 及其旧路由更新链路，不修改业务实例、包目录和部署目录。

### 阶段二：导入现有路由

根据真实业务入口显式创建独立规则，例如：

```text
旧：/mods/system/{path}
目标：fcj-platform / system
新下游：/fcj_common_api/{path} 或 /mods/system/{path}
```

具体下游路径必须根据业务服务真实接口确认，不能从旧 `RoutePrefix` 自动猜测或自动导入。

### 阶段三：切换入口

- 在 `air.gateway` 保持原有转发目标为 `air.forge`。
- 在 AirForge 路由管理中启用新规则。
- 观察命中率、目标选择、下游状态码和未匹配请求。
- 确认现场入口全部配置为动态规则后直接切换，不设置旧硬路由 fallback。

### 阶段四：清理旧职责

- 移除 Gateway 从路径第一段解析 ModId 的代码。
- 移除全局 `DynamicAppId` 对入口路由的强制筛选。
- 删除 `RoutePrefix` 字段、旧 `/routes/update` 语义、旧面板编辑器和相关文档。
- 更新文档、面板文案和部署样例，避免继续把 `/mods/{modId}` 描述为固定协议。

## 11. 可观测性与安全

每次转发至少记录：

- `RouteId`
- 上游方法和路径
- 目标应用、Mod、版本、DeploymentId
- 轮询或指定实例模式
- 下游路径（脱敏查询参数）
- 状态码和耗时
- 未匹配、目标不存在、目标不健康、下游失败等错误原因

日志不得记录 `Authorization`、`appSecret`、签名、请求体和其他敏感头。

路由管理 API 继续使用现有控制面会话或 Manager Ticket，并要求：

- 只有授权用户可以创建、修改、删除和启停路由。
- 路由目标必须在当前 AirForge 可见的状态范围内。
- 禁止通过下游模板访问任意外部 URL；下游只能使用已注册的目标实例 BaseAddress。
- 防止路径模板产生 `..`、反斜杠或协议注入。

## 12. 测试计划

### 单元测试

- 固定路径和 `{path}` 模板匹配。
- 路径段边界匹配，避免前缀误命中。
- HTTP 方法匹配。
- 优先级和规则具体度排序。
- Ocelot 风格固定段、单段参数和尾部捕获参数解析。
- 上游参数到下游模板替换。
- 查询字符串原样保留。
- 指定实例选择。
- 未指定实例轮询及轮询计数隔离。
- 实例不健康、实例不存在、版本不存在。
- 路由规则校验和冲突检测。
- 路由文件原子保存与重启加载。

### 集成测试

- Manager API 创建、更新、删除、启停路由。
- 路由变更后 Gateway 无需重启即可生效。
- `air.gateway -> air.forge -> 目标实例` 的 HTTP 方法、请求头、请求体和响应码转发。
- `/001/002/{path}` 转发到 `/mods/system/{path}`。
- 未指定实例时在两个健康实例之间轮询。
- 指定实例时不会落到其他实例。
- AirForge 重启后路由表和实例状态均可恢复。
- 目标版本或指定实例不可用时返回结构化错误且不误报为路由未匹配。

## 13. 验收标准

- AirForge 不再要求上游路径使用 `/mods/{modId}` 格式。
- `DynamicAppId` 不再作为 AirForge 入口路由的全局唯一筛选条件。
- 可在路由管理页面配置任意上游模板和下游模板。
- 可选择目标应用、目标 Mod、目标版本和指定实例。
- 未指定实例时只在 `Active + Healthy` 实例中轮询。
- 指定实例不健康或不存在时返回明确错误，不静默切换实例。
- 路由变更不重启业务进程，不修改包目录和部署目录。
- `air.gateway` 只负责将请求送到 `air.forge`，AirForge 完成目标选择和路径转换。
- 现场请求可以通过配置实现：

```text
/mods/system/hffcj_common_api/manage/init
  -> fcj-platform / system / 自动轮询
  -> /fcj_common_api/manage/init
```

- 所有单元测试、集成测试和远端验证通过后，才宣称动态路由升级完成；不设置旧硬路由兼容层。
